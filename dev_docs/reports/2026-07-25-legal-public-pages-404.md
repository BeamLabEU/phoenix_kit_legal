# Public legal pages 404'd on every host app — root cause and fix

**Date:** 2026-07-25
**Repos:** `BeamLabEU/phoenix_kit_legal` (fix, 0.1.6 → 0.1.7), `BeamLabEU/phoenix_kit_publishing` (docs only)
**Reported by:** user report via ClearSteps (`curl /legal` → 404, no `/legal` route in `router.ex`, no LiveView in `lib/clear_steps_web/live/`)
**Severity:** production outage on public compliance pages — the links the cookie consent widget shows to every visitor

---

## Summary

`phoenix_kit_legal` 0.1.6 declared `"legal"` as a reserved top-level route prefix,
which tells `phoenix_kit_publishing`'s catch-all dispatch to leave `/legal` alone so
a host-app LiveView can own it. No such LiveView ships with the module, none is
generated by the installer, and none was ever documented. For any host app that
hadn't hand-written one, the reservation removed `/legal` and `/legal/:slug` from
Publishing's dispatch with nothing taking over — so pages that had been rendering
since the module shipped started returning 404.

The reservation was reverted in 0.1.7. Legal pages are once again served by
Publishing as an ordinary group, which is the module's original design.

---

## Background: how the module is supposed to work

Legal does not render public pages. It generates them from EEx templates and stores
them as `phoenix_kit_publishing` posts in a group slugged `"legal"`
(`@legal_blog_slug`, `legal.ex:63`). Publishing's `/:language/:group/*path` dispatch
then serves them like any other group:

| URL | Renders |
|-----|---------|
| `/legal` | Index of published legal pages |
| `/legal/privacy-policy` | That page |
| `/en/legal/privacy-policy` | Same page, explicit locale |

The division of labour — **Legal generates content, Publishing renders it** — is what
gives legal pages per-language versions, translation, in-place editing, canonical /
`og:*` / hreflang tags, and the language switcher without a second rendering path.

## What went wrong

### The original defect (real)

Publishing's public controller never assigned `:url_path`. Host root layouts build
canonical / `og:url` / hreflang from that assign, so every publishing-served page
fell back to the layout's `"/"` default and canonicalized to the homepage. Google
dropped the affected pages as duplicates. Documented in Publishing's own source:

> every page served by this controller fell back to the layout's `"/"` default and
> canonicalized to the homepage (e.g. hydroforce.ee's `/legal` pages all pointed
> their canonical at `"/"`, and Google dropped them as duplicates)
>
> — `phoenix_kit_publishing/lib/phoenix_kit_publishing/web/controller.ex:55-61`

### The fix that was chosen (route-around)

`phoenix_kit_legal` PR #9 / commit `8b6610c` implemented
`reserved_route_prefixes/0 -> ["legal"]`, routing `/legal` away from Publishing's
generic post view so a host LiveView could render it with correct metadata instead.
Supported by `phoenix_kit#614` (the callback) and `phoenix_kit_publishing#29` (the
dispatch consults it).

### Why that was the wrong fix

**1. The underlying defect was fixed at its source the same day.**
`phoenix_kit_publishing` 0.2.3 (2026-07-03) shipped PRs #27–#29 together. Two of its
"Fixed" entries are the `assign_url_path` plug in `Web.Controller` — which repairs
canonical/`og:url`/hreflang for *every* publishing-served page — and the
reserved-prefix hole. Once the plug landed, the reservation's stated benefit was
gone; only its cost remained.

**2. It handed the route to something that does not exist.**
`LegalLive` appears nowhere in either package — no module, no scaffold, no generator
output, no documentation. Grepping both repos, the only occurrences are in PR #9's
own review doc, which assumes it. The commit message says the reservation prevents
Publishing rendering "instead of the host's `LegalLive`", presupposing a component
that was never built or specified.

**3. It was mandatory, not opt-in.**
Every host app installing the module got the reservation. The work required to make
it pay off was never communicated, so the default outcome was a 404.

**4. Nothing documented the contract.**
Neither README mentioned that the host app must own `/legal`. The only written trace
of the routing rule was a source comment in Publishing's `router_dispatch.ex:225` —
which is exactly what the reporting user had to dig up. This is why the regression
was hard to attribute.

### Why the blog was unaffected

The reporter noted that `blog_live.ex` was removed in `7db9c55` when the blog moved
to native Publishing rendering, and that this caused no problem. Correct: `"blog"`
is not reserved, so Publishing's dispatch kept serving it. `/legal` differed only in
carrying a reservation that removed it from that dispatch.

## The fix

`phoenix_kit_legal` 0.1.7:

- **`lib/phoenix_kit_legal/legal.ex`** — removed the `reserved_route_prefixes/0`
  implementation. `use PhoenixKit.Module` injects a `[]` default
  (`phoenix_kit/lib/phoenix_kit/module.ex:471`), so the callback still exists and
  returns empty; Publishing's `known_group?/1` stops treating `"legal"` as reserved
  and resumes serving the group. Replaced with a comment recording why it must stay
  unimplemented.
- **`test/phoenix_kit_legal/reserved_route_prefixes_test.exs`** — inverted from
  pinning `["legal"]` to pinning `[]`, so reintroducing the reservation without also
  shipping a renderer fails the suite.
- **`README.md`** — new "Public Legal Pages" section: no router changes needed, URL
  table, the published-vs-draft gate, `get_published_legal_links/0`, why a custom
  host `/legal` route can't work, and an upgrade note for anyone who added a
  workaround route.
- **`AGENTS.md`** — "Public Route Contract" section, including the constraints that
  bite when editing page-generation code (draft gate, the hardcoded `/legal/{slug}`
  shape in `get_published_legal_links/0`, and that renaming `@legal_blog_slug`
  changes public URLs).
- **`mix.exs`** — version bump; also corrected the dep-floor comment, which
  justified `~> 1.7.189` by the now-removed callback. The floor itself is unchanged
  (Checkbox attrs + runtime schema-prefix support).

`phoenix_kit_publishing` (documentation only, no code change):

- **`README.md`** — "How Dispatch Works", explaining the `call/2` override, why a
  host route whose first segment matches a group slug never matches regardless of
  declaration order, and the `mix phx.routes` internal-prefix surprise; plus
  "Reserved Route Prefixes", documenting the mechanism and warning that reserving
  without rendering yields a 404, citing this incident.

## Verification

- `mix quality.ci` (format check + `credo --strict` + `dialyzer`) — clean, 0 errors
- `mix test` — 38 tests, 0 failures
- `mix compile --warnings-as-errors` — clean
- Draft-gate claim in the README checked against
  `phoenix_kit_publishing/lib/phoenix_kit_publishing/web/controller/post_rendering.ex:60`
  (unpublished → `{:error, :unpublished}` → 404)
- Both dispatch shapes confirmed present in `RouterDispatch.maybe_rewrite/2`, so
  single-segment `/legal` and `/legal/:slug` both resolve

**Not verified:** no live host app was exercised. A `curl /legal` against a host
running 0.1.7 should be done before considering this closed.

## Host app action required

Host apps pick the fix up via `mix deps.update phoenix_kit_legal` (≥ 0.1.7). The
reservation lives in the installed package, so an app stays 404 until it updates.
Anyone who added a `/legal` route to work around 0.1.6 should remove it — Publishing's
dispatch claims the path in `call/2` before host routes are matched, so such a route
is dead code.

## Lessons

- **Fix defects at their source before routing around them.** Both fixes were in
  flight simultaneously; the route-around shipped anyway and outlived its rationale
  by one release.
- **Don't reserve a route without shipping its renderer.** The reservation's failure
  mode was silent and total: no compile error, no warning, no test failure — just a
  404 on production compliance pages.
- **A cross-package contract that lives only in a source comment will be missed.**
  The one artifact that described this behaviour was a comment in a *different*
  package, which is why diagnosis started from a user report rather than a doc.
